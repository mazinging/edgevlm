# M3 KV Cache 与跨模态调度 — 实测发现

> 数据：`results/m3_context_scan.json` + 诊断实验 | GTX 1650 Ti (SM 7.5) | SmolVLM-256M

## 1. 上下文/多图缩放实测

| 图片数 | tiles | seq_len | prefill (ms) | decode (ms/tok) | e2e (s) | KV (MB) | peak (GB) |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 79 | 189.8 | 44.48 | 0.90 | 3.64 | 1.21 |
| 2 | 2 | 146 | 360.9 | 45.80 | 1.09 | 6.73 | 1.36 |
| 4 | 4 | 280 | 677.7 | 46.03 | 1.41 | 12.90 | 1.65 |
| 8 | 8 | 548 | 1359.5 | 43.96 | 2.06 | 25.25 | 2.24 |

架构：30 层，**3 KV heads**，head_dim 64（GQA 9Q/3KV）

## 2. 发现 A（核心）：decode 延迟与上下文长度**无关**

**序列长度 ×6.9（79→548），decode 延迟 ×0.99（44.5→44.0 ms/tok）—— 完全持平。**

### 根因：decode 是 kernel 启动延迟受限，不是 KV 带宽受限

**证据 1：KV 访存耗时占比 <1%**

| seq | KV 大小 | 理论读取耗时 (÷171 GB/s) |
|---|---|---|
| 548 | 25.25 MB | **0.148 ms** |
| 2048 | 94.37 MB | 0.552 ms |
| 8192 | 377.49 MB | 2.206 ms |

实测 decode = 44 ms/tok → seq=548 时 KV 访存仅占 **0.34%**；即使 seq=8192 也只占 5%。

**证据 2：kernel 启动开销精确解释了 44ms**

| 串行小 matmul 数 | 耗时 | 每 kernel |
|---|---|---|
| 1 | 0.253 ms | 0.253 ms |
| 30 | 6.909 ms | 0.230 ms |
| **210** | **46.690 ms** | **0.222 ms** |

模型 30 层，每层约 7 个 kernel → **~210 个 kernel × 0.222ms ≈ 46.7ms**，
与实测 44ms/tok 高度吻合。

**结论**：decode 每步只处理 1 个 token（M=1），
每个算子都是极小 kernel，GPU 全程在"启动-等待"，
**算力和带宽都远未饱和**。

## 3. 发现 B（重要负面结论）：本平台上 KV Cache 量化不值得做

标准做法是把 KV Cache 量化到 INT8 以省带宽。**但本机数据说明这是无效优化**：

| 若做 KV INT8 量化 | 理论收益 |
|---|---|
| KV 访存从 0.148ms 降到 0.074ms | **省 0.074 ms** |
| decode 单 token 总耗时 | 44 ms |
| **端到端收益上限** | **0.17%** |

**加上量化/解量化的 kernel 开销，实际是负收益。**

> **这是一个诚实且有价值的负面结论**：KV Cache 量化在
> **长上下文 + 大 batch + 带宽受限**的场景（如服务端高并发）才有效；
> 在**端侧单流短上下文**场景，瓶颈在 kernel 启动开销，KV 量化解决不了问题。
> JD 第 3 条要求"结合业务场景探索优化方案"，这就是一个具体例证。

## 4. 发现 C：真正的杠杆是批处理，不是 KV

| batch | e2e (s) | 总吞吐 (tok/s) | 单流 (ms/tok) |
|---|---|---|---|
| 1 | 1.50 | 10.68 | 93.59 |
| 2 | 1.71 | 18.69 | 107.00 |
| 4 | 1.98 | 32.27 | 123.96 |
| **8** | 2.73 | **46.90** | 170.58 |

bs=1 → 8：**吞吐 ×4.4，而单流延迟仅 ×1.8**。

原因：batch 增大把 M=1 的小 GEMM 变成 M=8 的 GEMM，
**摊薄了固定的 kernel 启动开销**。

> 这与 M2 的发现形成呼应：
> M 变大 → kernel 启动开销被摊薄 + INT8 Tensor Core 变为可用。
> **批处理是同时解锁这两者收益的钥匙。**

## 5. 发现 D：prefill 随序列线性增长（符合预期）

| seq | prefill (ms) | 相对 seq=79 |
|---|---|---|
| 79 | 189.8 | 1.00× |
| 146 | 360.9 | 1.90× |
| 280 | 677.7 | 3.57× |
| 548 | 1359.5 | 7.16× |

序列 ×6.9 → prefill ×7.16，**近似线性**。
说明 prefill 的 M=seq_len 较大，能充分利用 GPU（与 decode 形成鲜明对比）。

→ **prefill 是 INT8 能发挥作用的场景**（M2 已证 M≥128 时加速 3.89×）。

## 6. 优化方向的重新定位（数据驱动）

基于以上实测，本平台的优化优先级应为：

| 方向 | 数据支持的收益 | 优先级 |
|---|---|---|
| **批处理 / continuous batching** | 吞吐 ×4.4 @ bs=8 | ⭐⭐⭐ |
| **INT8 用于 prefill（M 大）** | M=128 时 3.89× | ⭐⭐⭐ |
| **减少 kernel 启动数（算子融合 / CUDA Graph）** | decode 44ms 中绝大部分是启动开销 | ⭐⭐⭐ |
| CUDA Graph 捕获 decode | 可消除逐 kernel 启动开销 | ⭐⭐⭐（M4 验证） |
| KV Cache 量化 | **0.17% 上限** | ⭐ 不做 |
| W4A16 | 负收益（M2 已证） | ⭐ 不做 |
| 视觉 token 剪枝 | 单图仅影响 10.9%（M1） | ⭐⭐ 多图场景才值得 |

## 7. 方法论要点

1. **先测瓶颈，再选优化**。直觉认为"长上下文 → KV 是瓶颈"，
   实测证明在本平台根本不成立（KV 访存 <1%）。
2. **区分 latency-bound 与 bandwidth-bound**：
   用「理论访存耗时 / 实测耗时」判断，比凭经验猜更可靠。
3. **负面结论同样有价值**：明确"不该做什么"能避免团队浪费工程投入。

## 8. M3-B：kernel 剖析与启动开销优化

### profiler 实测（1 次 generate，8 新 token）

| kernel | 调用次数 | CUDA 时间 | 占比 |
|---|---|---|---|
| `aten::matmul` | **2201** | 195.9 ms | 10.45% |
| `aten::as_strided` | **9433** | 148.6 ms | 7.93% |
| `aten::mm` | **1689** | 145.0 ms | 7.74% |
| `aten::mul` | 2223 | 132.9 ms | 7.10% |
| `aten::reshape` | 3549 | 125.6 ms | 6.70% |
| `aten::slice` | 3793 | 116.5 ms | 6.22% |
| `aten::transpose` | 3033 | 99.9 ms | 5.33% |
| `aten::addmm` | 72 | 85.2 ms | 4.55% |
| `aten::add` | 1738 | 77.7 ms | 4.15% |
| `aten::linear` | 1761 | 69.7 ms | 3.72% |
| `aten::bmm` | 512 | 62.7 ms | 3.35% |
| `aten::view` | 3662 | 62.0 ms | 3.31% |

**关键观察**：
- 单次 generate 触发 **2201 次 matmul、9433 次 as_strided** —— 海量微小算子。
- **真正的矩阵乘只占 10.45%**；大量时间花在
  `as_strided`/`reshape`/`transpose`/`slice`/`view` 等**纯内存布局操作**上。
- 这是 M=1 逐 token 推理下 PyTorch **eager 模式框架开销**的典型特征：
  框架在张量视图元数据上的开销超过了实际计算。

### 优化手段实测对比

| 手段 | tok/s | 加速 | 结论 |
|---|---|---|---|
| eager 基线 | 10.61 | 1.00× | — |
| **torch.compile** (reduce-overhead) | 10.10 | **0.95×** | ❌ **无收益，略负** |
| 批处理 bs=2 | 18.17 (总) | 1.71× | ✅ |
| 批处理 bs=4 | 30.30 (总) | 2.86× | ✅ |
| **批处理 bs=8** | **47.32 (总)** | **4.46×** | ✅ **最有效** |

**`torch.compile` 在此场景无效**（0.95×）：推测因 M=1 的动态形状导致
反复重编译 / 图断裂，且 `reduce-overhead` 的 CUDA Graph 收益
被动态 shape 打断。**这是一个诚实的负面结果**——
说明"用 torch.compile 一键加速"在端侧逐 token 解码场景并不成立。

### 最终优化结论（数据驱动）

| 方向 | 实测收益 | 结论 |
|---|---|---|
| **批处理（continuous batching）** | **吞吐 ×4.46 @ bs=8** | ⭐⭐⭐ 首选 |
| INT8 用于 prefill（M≥128） | 3.89×（M2 实测） | ⭐⭐⭐ |
| KV Cache 量化 | **≤0.17% 上限** | ❌ 不做 |
| W4A16 | 负收益（M2 实测） | ❌ 不做 |
| torch.compile | 0.95× | ❌ 本场景无效 |
| 视觉 token 剪枝 | 单图 ≤10.9%（M1） | ⭐⭐ 仅多图场景 |

> **核心洞察**：端侧单流解码的瓶颈是 **kernel 启动/框架开销**，
> 不是算力也不是带宽。因此：
> - **省带宽的优化（KV 量化、W4A16）无效**
> - **省算力的优化（INT8 TC）需 M 足够大才生效**
> - **真正有效的是「增大 M」**——批处理或 prefill，二者都能摊薄固定开销
